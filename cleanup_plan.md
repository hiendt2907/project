# Implementation Plan: System Cleanup & Verification

> **Canonical:** [docs/vendor/OMNI_PROJECT_CANONICAL.md](docs/vendor/OMNI_PROJECT_CANONICAL.md). Historical plan.

This plan addresses the "log noise" and errors currently being generated by the Watchdog and PostgreSQL gateway, while verifying that the event pipeline is correctly processing data.

## Proposed Changes

### 1. Watchdog Fix (Stop Log Spam)

#### [MODIFY] [watchdog.py](file:///Users/hiendang/project/src/sre/watchdog.py)
*   **Remove** `show pool_nodes;` query. asyncpg is routing this to standbys which causes errors.
*   **Replace** with a simple `SELECT 1;` health check to verify connectivity to the gateway.
*   Extend the polling interval to 5 minutes or make it configurable to reduce activity.

### 2. Connection Cleanup (Reduce SQL Noise)

#### [MODIFY] [pgvector_store.py](file:///Users/hiendang/project/src/rag/pgvector_store.py)
*   **Guard** `ensure_ready()` with a session-level flag. It should only run once when the application starts, not on every operation attempt if already successful.
*   This will stop the constant `NOTICE: relation ... already exists` in the logs.

### 3. Pipeline Verification

#### [TEST] [event-trigger]
*   Use `curl` from within the cluster (or via a temporary pod) to send a test JSON event to `omni-gateway`.
*   Monitor `omni-worker` logs to confirm it receives and processes the new message.

## Verification Plan

### Automated Tests
*   `kubectl logs -n multi-agent deployment/pgpool-gateway -f`: Verify that the `unrecognized configuration parameter` errors STOP.
*   `kubectl logs -n multi-agent deployment/omni-worker -f`: Verify that only relevant processing logs appear.

### Manual Verification
*   Check the `doc_errors` table to see if the watchdog or worker recorded any new legitimate errors.
